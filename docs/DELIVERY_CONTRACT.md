# Delivery evidence contract v1

Status: schema 1 delivered in DocKit 4.16.0; not deployment authorization.

## Boundary

DocKit validates records and writes them under a lock. It does not execute a
probe, deployment, recovery, infrastructure change or authority transition.
The opted-in project entrypoint runs its reviewed probe, records evidence,
then calls `dockit-delivery-record.sh begin` immediately before mutation.
`begin` validates and reserves the attempt atomically; a read-only check alone
is not a reservation. Recovery is a separate project path and remains available
even when ordinary validation or the journal is damaged.

A project is not protected merely because these files were copied. Adoption
requires a rerunnable negative integration test in the project repository and
a fresh receipt bound to the declared entrypoint/probe/test/implementation.
The application remains responsible for real observations, evidence redaction,
causal equivalence, authority and recovery. No new ForgeOS runtime is required.

## Declaration

Use a reviewed, committed `docs/llm/delivery/<work>.contract`, restricted flat
`key=value` lines; blank lines and `#` comments are allowed. No shell evaluation,
YAML generality, whitespace in values, unknown keys or duplicate scalar keys.

```
schema=1
work=remote-access
environment=development
entrypoint=scripts/accept-remote.sh
probe=scripts/probe-remote.sh
negative_test=scripts/test-remote-refusal.sh
outcome=docs/operations/REMOTE_ACCEPTANCE.md
authority=docs/operations/REMOTE_AUTHORITY.md
max_age=300
integration_max_age=86400
attempt_limit=2
review_limit=2
prerequisite=ingress
binding=scripts/remote-lib.sh
```

Paths are project-relative regular files without traversal or symlink parents.
The entrypoint, probe, negative test, outcome/authority, extra bindings and declaration bytes form
the candidate digest. Include every implementation/config artifact the command
loads. Outcome/authority are existing evidence references, not new permissions.
Prerequisite IDs are declaration-owned and stable across packets/versions.
Changes within a registered declaration require explicit reassessment. The key is
the declared environment/outcome reference: changing both work and outcome paths
can create a new identity. Operator reassessment must preserve predecessor work;
the checker cannot infer that differently named outcomes are semantically equal.
The same environment/outcome reference has one registered work identity in the Git
common directory, preventing a second work name from silently resetting it.

## Journal and checkpoint

Use full Git history; shallow clones must fetch it before initializing/restoring.
The helper maintains `<work>.log` beside the declaration, with fixed delimited
records generated by the helper. Keep it in Git as durable evidence when handing
off across clones; committing journal-only changes needs no product release.
Ensure project ignore rules do not hide it (for example append
`!docs/llm/delivery/*.log` after a generic `*.log` rule). Verify the journal is
tracked before a cross-machine handoff; no clone can restore never-published events.
A checkpoint and last-good journal under the Git common directory preserve
uncommitted events across sessions/worktrees. Every operation verifies the full
checkpoint. Committed prefix verification is cached only while Git refs and HEAD
remain unchanged. Missing, rewritten or truncated history
fails closed. Registration refuses an existing/deleted historical identity.
Fresh-clone restoration is explicit and accepts only the exact committed journal.

Writers serialize with an atomic directory lock. A pending transaction preserves
before/after bytes so a crash cannot silently discard events. A refused ordinary
operation does not prevent a project from restoring its runtime; journal repair
must then reconcile retained evidence. This detects accidental/ordinary rewriting,
not an adversary controlling Git history and every local checkpoint.

## Evidence and candidate review

The project probe writes a restricted evidence file:

```
prerequisite=ingress
environment=development
observed_at=1790000000
status=pass
cause=public-ingress-restored
```

`cause` is the adapter's canonical causal state; timestamps, peer names, release
names and arbitrary digests are not causal changes. The reviewed adapter defines
normalization. The recorder binds evidence to the current candidate, rejects
unknown fields/IDs, future observations and wrong environments. The entrypoint
requires all prerequisites passing and fresh at the actual `begin` call.

Review records bind a candidate digest to `approved` or `changes`, blocker count
and an existing review-evidence file. An approval with blockers is invalid.
Any unresolved blocker prevents ordinary readiness; a new candidate cannot erase
it. Subsequent review explicitly reconciles findings. Review rounds are counted
from the journal; passing the provisional limit requires bounded reassessment,
never automatic GO. The current kit candidate still uses the LLM-DocKit independent-review-policy
process (D-020 provenance requirements, current model preference under D-024), not an unimplemented limit on its own development.

## Operations

All commands require `--project PATH --contract RELPATH`. The recorder supports:

- `init`: register a committed declaration with no historical journal.
- `restore`: recover an exact committed ledger in a fresh clone, never reset it.
- `evidence --file PATH`: append a probe observation.
- `review --verdict approved|changes --blockers N --file PATH`: record the
  external D-020 review; file contents are hashed, never copied into the log.
- `integration`: execute the declared negative test using its executable shebang;
  retain its private output artifact and append a hashed receipt only if it
  succeeds and the candidate/journal remain unchanged. A clone reruns this test.
  The test runs with the caller's privileges/environment and no built-in timeout;
  it must provide bounded execution and isolate any side effects in disposable
  resources. The helper detects only candidate/journal changes, not arbitrary
  side effects. Its output must be sanitized.
- `repair`: finish a retained append, or reconstruct a missing checkpoint only
  from identical retained and current journal bytes.
- `begin`: validate and reserve one attempt, returning its stable sequence ID.
- `finish --attempt N --result success|failure --recovered yes|no`: close the
  reservation. Failure without complete recovery blocks ordinary continuation.
- `recovered --attempt N --file PATH`: record attributed recovery evidence.
- `reassess --file PATH --attempts N --reviews N --owner TOKEN`: record a bounded extension
  within existing authority; never waive prerequisites, blockers or recovery.

Any previously failed causal prerequisite snapshot remains blocked until explicit
reassessment, including A-to-B-to-A alternation and intervening success.
Candidate changes and new timestamps do not reset this comparison or counters.
A reviewed redesign can be recorded by reassessment; its scope/evidence must be
explicit and cannot manufacture a passing prerequisite or review verdict.

The read-only checker does not hold the writer lock and can report a transient
checkpoint mismatch during an append; rerun it after the writer finishes. Only
`begin` provides a serialized reservation.

`dockit-delivery-check.sh` reports status, candidate, counts and blocker. Its
`--recovery` mode explicitly reports that DocKit places no ordinary-delivery
barrier on the project's separately authorized recovery path. It is never a
command executor. Usable outcomes are declared criteria plus attributed real
acceptance evidence, not a truth claim inferred by DocKit.

## Acceptance

Tests must reproduce absent/failed/stale/wrong-context prerequisites before any
mutation, renamed equivalent retries, changed causal evidence, unresolved review
findings, exhausted budgets, interrupted/unfinished recovery, concurrent begin,
resume/clone continuity, history rewriting, and stale integration evidence.
A real adopter must exercise its actual entrypoint and intended user path before
incident-remediation acceptance. A fixture, source release or copied script does
not satisfy that gate. Source/deployed/usable states remain distinct.

## Local recovery and limits

The scripts use POSIX shell/awk plus Git, `mktemp`, `date +%s`, and `head -c`;
the tested platform is Linux. Probe observations expire after `max_age` seconds
(1..86400); integration receipts have their own `integration_max_age` (default
86400, maximum 604800). Candidate changes invalidate both immediately.

The Git common-directory store contains a lock owner record (PID, host, action,
time and worktree). Never remove a live writer's lock. For an abandoned lock,
verify that recorded process/worktree has stopped, preserve the store and journal,
then remove only that lock directory. Run `repair` if a retained `pending`
transaction exists; it only completes exact prefix-consistent appends. This is
process-interruption recovery, not a guarantee against storage hardware failure.

If no pending transaction exists but a checkpoint is missing, preserve all copies.
An intact `last-good` file must match the current journal before an operator can
run `repair` to reconstruct only its missing hash checkpoint. A conflicting
existing hash is never replaced. Repeating `repair` against an already consistent
checkpoint is a no-op; neither repair path grants ordinary readiness. A missing identity, divergent copies or lost
uncommitted events require evidence reconciliation; `init` is never recovery.
A genuinely fresh clone uses `restore` on the exact committed history. That cannot
recover events that were never committed or backed up from the original machine.
Runtime recovery remains independently available throughout; the `--recovery`
message merely states that ordinary delivery gates do not apply to that path.

Review/probe files are hashed, not retained by the journal: preserve their
sanitized contents in the project's evidence store. The negative test output is
retained locally with restrictive permissions; the project must redact secrets.
A project with authority over Git and all local copies can bypass these controls;
this is continuity and accidental-drift detection, not an adversarial trust root.

Keep mutable acceptance/review receipts separate from the bound outcome/authority
specification: editing a bound document invalidates earlier approval, observations
and integration. Adopter integration tests should compare declared bindings with
the complete tracked inputs their command loads, including newly added files.
Empty regular extra inputs are valid bindings; required control documents are not.

Retained integration outputs have no automatic pruning. Back up required evidence
before manually removing old artifacts; never remove the hash referenced by the
current integration event or readiness fails until a fresh test run. The initial
integration checkpoint is also advisory/unlocked and may need retry after a
concurrent writer finishes; no attempt is reserved by that test.
