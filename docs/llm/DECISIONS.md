## D-001 - Restricted flat grammar for sync manifest

**Status:** accepted

### Decision
The dockit-sync-manifest.yml uses a restricted flat grammar parsed with grep/sed/awk, not a generic YAML parser.

### Context
dockit-sync.sh is POSIX sh — no ruby, python, or yq available as guaranteed dependencies. The manifest needs to map file paths to sync strategies (copy, skip, section-merge, yaml-merge).

### Options Considered
1. Generic YAML parser (yq/python) - Full YAML support but adds external dependency
2. Restricted flat grammar (key: value per line) - Limited but zero dependencies
3. JSON config - Harder to hand-edit, still needs parser

### Rationale
Zero-dependency constraint wins. The manifest schema is simple enough (path + strategy + optional flags) that a flat grammar covers all current needs. The schema_version field allows future migration if complexity grows.

### Implications
- No nested YAML structures in manifest
- Adding new fields requires updating the parser in dockit-sync.sh
- schema_version: 1 locks current format

### Follow-ups
- Revisit if manifest needs grow beyond flat key-value pairs

## D-002 - Runtime state in .git/.dockit/

**Status:** accepted

### Decision
All dockit-sync runtime state (state.yml, backups, lock files) lives in `.git/.dockit/` inside each downstream project.

### Context
Sync state needs to persist between runs but should not be committed to downstream repos. Options: dotfile in project root, XDG data dir, or inside .git/.

### Options Considered
1. `.dockit/` in project root - Visible, requires .gitignore entry in every downstream project
2. `~/.local/share/dockit/` (XDG) - Clean separation but loses locality (state disconnected from repo)
3. `.git/.dockit/` - Auto-ignored by git, co-located with repo, no .gitignore changes needed

### Rationale
`.git/.dockit/` is automatically excluded from git tracking (anything inside `.git/` is ignored). This avoids polluting downstream `.gitignore` files and keeps state co-located with the repo it belongs to. Trade-off: state is lost if `.git/` is deleted, which is acceptable since `--init-state` can regenerate it.

### Implications
- No .gitignore modifications needed in downstream projects
- State lost on fresh clone (regenerated by --init-state)
- Backups stored at `.git/.dockit/backups/` with timestamps

### Follow-ups
- None currently

## D-003 - CONFLICT without --force triggers full rollback

**Status:** accepted

### Decision
When dockit-sync detects a merge conflict during section-merge or yaml-merge, it rolls back all changes made in that sync run and writes no state. The `--force` flag is required to override.

### Context
A partial sync (some files updated, others conflicting) leaves downstream in an inconsistent state. The tool must either commit partial results or roll back entirely.

### Options Considered
1. Partial commit - Apply what works, skip conflicts, update state for successful files
2. Full rollback - Restore all files from backup, write no state, report error
3. Interactive resolution - Prompt user per conflict (not viable in POSIX sh scripts)

### Rationale
Full rollback is the safest default. A partial sync could leave template-managed sections at different versions within the same project, creating subtle inconsistencies. The user can review the dry-run output, fix conflicts manually, then re-run. `--force` exists as escape hatch for cases where the user explicitly accepts override.

### Implications
- Sync is atomic: all files update or none do
- Backups are created before any modifications
- --force bypasses conflict detection (use with caution)
- Dry-run mode (default) previews all changes before apply

### Follow-ups
- None currently

## D-004 - OUTDATED uses string compare, not SemVer

**Status:** accepted

### Decision
dockit-sync-check.sh determines if a downstream project is OUTDATED by comparing the `template_version` string stored in the project's state file against LLM-DocKit's current VERSION. This is a plain string compare, not SemVer parsing.

### Context
Need to determine if downstream files match the template versions. Could compare version strings semantically (SemVer), compare actual file content (hashes), or compare timestamps.

### Options Considered
1. SemVer comparison - Parse and compare major.minor.patch semantically
2. String comparison of template_version - Simple equality check, no parser needed
3. Content hash comparison - SHA256 of each synced file, catches all drift including whitespace
4. Timestamp comparison - Compare modification times (unreliable across git clones)

### Rationale
String comparison of `template_version` is the simplest approach that works: if the downstream state records version "4.0.0" and the template is now "4.1.0", the strings differ → OUTDATED. No SemVer parser needed in POSIX sh. The `(partial)` suffix in output is a detail indicator for adoption mode, not a separate state.

### Implications
- Only detects version bumps, not content-level drift within the same version
- Simple and fast (grep + string equality)
- States: CURRENT | OUTDATED | NO_STATE
- Does not catch manual edits to downstream files that don't change the version

### Follow-ups
- Consider adding content-hash checks as a stricter optional mode
- Corrected 2026-03-01: original D-004 text incorrectly described SHA256 hash comparison; actual implementation uses template_version string compare (verified against scripts/dockit-sync-check.sh)
