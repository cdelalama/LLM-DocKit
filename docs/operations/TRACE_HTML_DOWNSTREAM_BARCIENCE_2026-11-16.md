# Downstream input: HTML Trace prototypes from barcience-survey (2026-11-16)

Status: input for comparison, not a decision. Author: Claude Code (claude-opus-5-5),
advisor role, in an Orca chat on OCTA working in `cdelalama/barcience-survey`.
Recorded in DocKit on 2026-11-27 at Carlos's request so the DocKit Trace work
(4.23.0, `scripts/dockit-trace-render.py`, three layout previews) can be compared
with it. No independent review: Claude author; this note is a report, not a
policy change.

## What was done

On 2026-11-16, before DocKit 4.23.0 existed, Carlos asked for a Trace header
rendered as HTML through Orca's inline visuals (`ORCA_CHAT_SCRATCH_DIR` plus a
`::orca-visual{file=...}` line), as a candidate for the protocol. Two hand-written
prototypes were shown; both files are kept here unchanged:

1. `trace-html-barcience-2026-11-16/trace-header-prueba-01.html` - plain card:
   role pill, subject and Sent on one row; three cells (resulting state, repo,
   validation) with green/amber/grey pills; a "next step" band. Only Orca theme
   tokens with fallbacks. Carlos: it works, but he does not like the look.
2. `trace-html-barcience-2026-11-16/trace-header-prueba-02.html` - richer and
   interactive: gradient frame, role initial, large local clock with UTC
   underneath, four cards with a status dot, highlighted "next step (who acts)",
   and buttons: copy the text Trace to the clipboard (`navigator.clipboard`,
   falling back to `execCommand`), show the text version, a four-checkbox test
   with a progress bar, and an accent colour switch. Local colours use their own
   variables (`--tr-a`, `--tr-b`) so Orca tokens are never redefined.

Result: both render inside Orca. Carlos did not report which of the buttons in
prototype 2 worked (the clipboard is the one most likely to be blocked), so
interactivity is **not verified** and should be tested in the DocKit previews.

## Proposal made in that session

- The text Trace stays mandatory in every client; HTML is an added presentation
  only when the Orca capability exists. Terminal, Codex and exported transcripts
  only see the `::orca-visual` line. (DocKit 4.23.0 already does this.)
- The HTML must be generated by the script from the real Git/clock snapshot, not
  written by the model. (DocKit 4.23.0 already does this with
  `dockit-trace-status.sh` and `dockit-trace-render.py`.)
- Limit the HTML to substantive turns: each one costs a file in the chat folder
  and one more tool call.
- Worth considering in the chosen layout: a "copy text Trace" button (useful to
  paste into HISTORY or another agent's window) and visible "who acts next".
  A button cannot send anything back to the agent; the page has no network or
  Orca access, so answers must still be typed in the chat.
- Wide screens: Orca decides the chat column width; the agent cannot widen the
  text. A visual can use the full frame width with columns, but whether Orca
  lets a visual grow wider than the text column was not tested.

## Defect found that still exists in 4.23.0

On OCTA (Windows, Git Bash) `TZ=Europe/Madrid date` silently returns UTC labelled
`GMT`, because that `date` has no time-zone database. On 2026-11-16 this produced
a wrong hand-converted Sent in barcience-survey; the correct local time was taken
with PowerShell (`[TimeZoneInfo]` `Romance Standard Time`).

Re-checked on 2026-11-27 against DocKit `4913037`:
`scripts/dockit-trace-status.sh` line 154 uses `TZ="$LOCAL_TZ" date`, and a run
on OCTA emitted `Sent: 2026-11-26 23:02:32 Europe/Madrid (23:02:32 UTC)`, while
the real local time was 00:02:32 on 2026-11-27. The local field is wrong by the
UTC offset and even the date can be wrong, without any error. The test file the
run created in the Orca chat folder was removed.

Suggested fix, to be reviewed: detect that the zone was not applied (local equals
UTC while the configured zone is not UTC, or `%Z` prints `GMT`/`UTC`) and then
use a source that knows the zone (`python3 -c` with `zoneinfo`, or on Windows
PowerShell `[TimeZoneInfo]::ConvertTimeFromUtc`). If none is available, print
`Sent: unverified client time ...` as the protocol already requires, never a UTC
value labelled as local. Add a test that simulates a `date` that ignores `TZ`.
